## Что было: сайт отдавал 404 с 29 августа 2026

Всё остальное в этом файле — следствия. Замер 10.09.2026, до починки:

```
http://odin-dva.ru/       301 → https://odin-dva.ru/
https://www.odin-dva.ru/  301 → https://odin-dva.ru/
http://www.odin-dva.ru/   301 → https://odin-dva.ru/
https://odin-dva.ru/      404   ← сюда вели все три редиректа
https://odin-dva.ru/robots.txt        404
https://odin-dva.ru/sitemap.xml       404
https://odin-dva.ru/intervalnyj-tajmer.html  404
```

404 отдавал сам GitHub (`server: GitHub.com`, страница «Page not found · GitHub Pages»),
а не приложение. То есть Pages не обслуживал домен вообще.

### Причина

**GitHub Pages не отдаёт приватные репозитории на бесплатном плане.** Репозиторий
`colizej/1-2` был приватным, аккаунт — на Free.

Проверка, которая это подтвердила: у того же владельца публичный репозиторий с Pages
(`keypaste`) отдаёт 200, приватный `1-2` — 404. При этом:

- сборка Pages числится успешной (`status: built`, ошибок нет),
- DNS правильный: `odin-dva.ru` → `185.199.108-111.153`, `www` → `colizej.github.io`,
- `CNAME` с `odin-dva.ru` лежит в репозитории и в `origin/main`,
- последний коммит — 26.04.2026, то есть код никто не ломал.

Сломалось не в коде и не в DNS, а в биллинге: сайт перестал отдаваться 29.08.2026,
последний визит в Метрике — 28.08.

### Как чинили

| Шаг | Состояние |
|---|---|
| История репозитория проверена на секреты (ключи, токены, `.env`) | ✅ чисто, только код и своя синтезированная демо-музыка |
| Репозиторий переведён в публичный | ✅ 10.09.2026 |
| Pages пересобран | ✅ `status: built` |
| Владение доменом подтверждено TXT-записью | ✅ 10.09.2026 |
| Домен `odin-dva.ru` возвращён в настройки Pages | ✅ `cname: odin-dva.ru` |
| Sitemap переотправлен в GSC | ✅ предупреждений стало 0 |

Публикация репозитория сняла только половину проблемы: домен после неё не вернулся,
GitHub отвечал

```
The custom domain `odin-dva.ru` is already taken.
```

Домен числился за осиротевшей записью от прежней привязки. Ни за одним другим
репозиторием аккаунта он закреплён не был — проверено перебором всех 29 репозиториев,
`cname` стоял только у `keypaste`. Снимается такая запись единственным способом —
подтверждением владения доменом, и API для этого у GitHub нет, только веб-интерфейс:

1. <https://github.com/settings/pages> → **Add a domain** → `odin-dva.ru`
2. GitHub даёт TXT-запись `_github-pages-challenge-colizej.odin-dva.ru` со значением-токеном
3. Запись добавляется в зону у регистратора (домен на `ns1.reg.ru` / `ns2.reg.ru`)
4. После распространения — кнопка **Verify**

Две вещи, на которых это чуть не встало:

- **`ns1.reg.ru` и `ns2.reg.ru` расходятся.** Через две минуты после сохранения запись
  отдавал только `ns2`, `ns1` подхватил её ещё через пару минут. Жать **Verify** имеет
  смысл, когда оба сервера отвечают одинаково:
  `dig +short TXT _github-pages-challenge-colizej.odin-dva.ru @ns1.reg.ru`
- **Домен и HTTPS ставятся раздельно.** Запрос с `cname` и `https_enforced=true` разом
  падает с `The certificate does not exist yet`: сертификат выпускается только после
  того, как домен привязан. Сначала `cname`, потом HTTPS (он включился сам).

Проверка, что всё поднялось:

```bash
curl -sI https://odin-dva.ru/ | head -1     # ждём 200
python3 scripts/seo/fetch_gsc.py --days 28 --inspect 10
```

### Как не наступить снова

Сломалось не в коде и не в DNS, а в биллинге, и предупреждения об этом нигде не было:
сборка Pages всё это время числилась успешной. Единственный надёжный признак —
сам сайт. Если `odin-dva.ru` снова отдаст 404 при зелёной сборке, проверять в этом
порядке: публичный ли репозиторий → стоит ли `cname` в настройках Pages → жив ли
домен. Первые две проверки — одна команда:

```bash
gh api repos/colizej/1-2 --jq '.private'
gh api repos/colizej/1-2/pages --jq '"cname=\(.cname) status=\(.status)"'
```

## Деплой: Pages не пересобирается сам

Замечено 10.09.2026, после первого пуша с апреля.

Код доезжает до GitHub, но на сайт не попадает: `raw.githubusercontent.com` отдаёт
новый `static/app.js`, а `https://odin-dva.ru/static/app.js` — апрельский, с
`last-modified: 26 Apr`. Причина видна в списке прогонов: на коммит `d8bc262`
отработал только `Graph Update`, а `pages build and deployment` **не запустился**.
Последняя настоящая сборка Pages — от 26.04.2026.

Что уже пробовали, всё без результата:

| Попытка | Итог |
|---|---|
| `POST /repos/colizej/1-2/pages/builds` (несколько раз) | отвечает `queued`, новая сборка в списке не появляется |
| Переустановка источника (`source[branch]=main`, `path=/`) | ничего не изменилось |
| Явная установка `build_type=legacy` | ничего не изменилось |

Push на GitHub при этом регистрируется: в событиях репозитория есть `PushEvent`
от 14:41. Репозиторий публичный, домен `verified`, `status: built`.

Похоже на последствие того, что Pages двенадцать дней был отключён из-за приватности
репозитория: сайт числится собранным, но конвейер сборки к ветке больше не привязан.

Дальше есть два пути, оба требуют решения владельца:

1. **Пересоздать сайт Pages** — `DELETE`, затем `POST /pages` с источником `main` `/`
   и возвратом домена. Домен уже подтверждён на уровне аккаунта, так что повторно
   он не «занят». Риск — несколько минут недоступности.
2. **Перевести деплой на GitHub Actions** (`build_type: workflow` плюс workflow с
   `actions/upload-pages-artifact` и `actions/deploy-pages`). Дольше, но деплой
   становится видимым и отлаживаемым, а не молчаливым, как легаси-конвейер.

**На сайте сейчас апрельская версия.** Она рабочая — не отдаётся только то, что
добавлено 10.09: события аналитики в `static/app.js`. Пока конвейер не починен,
цели в Метрике ловить нечего.

## Индексация в Google

Проверено через URL Inspection API 10.09.2026, уже после восстановления. Инспекция
показывает состояние **последнего обхода**, а он пришёлся на простой — поэтому цифры
пока прежние и обновятся, когда Google придёт снова:

| URL | Вердикт | Последний обход |
|---|---|---|
| `/` | Проиндексирована | 12.07.2026 |
| `/intervalnyj-tajmer.html` | **Просканирована, но не проиндексирована** | 26.04.2026 |
| `/privacy.html` | **Не найдено (404)** | 09.09.2026 |
| `/terms.html` | **Не найдено (404)** | 10.09.2026 |

Читается так: Google переобходил сайт во время простоя и по мере обхода выкидывал
страницы из индекса. `privacy` и `terms` выпали 9 и 10 сентября. **Главная уцелела**
по случайности: последний успешный обход был 12 июля, а до следующего сайт успели
починить. Это и было главной причиной спешить — пока страница в индексе, она
возвращается сама; после выпадения переиндексация занимает недели.

`privacy` и `terms` вернутся в индекс при следующем обходе — переотправка sitemap
10.09 должна его ускорить. Специально запрашивать переиндексацию не нужно, но
проверить через неделю стоит:

```bash
python3 scripts/seo/fetch_gsc.py --days 28 --inspect 10
```

Отдельная история — `/intervalnyj-tajmer.html`. Её Google обошёл 26.04.2026 и решил
не индексировать: вердикт «Просканирована, но пока не проиндексирована» появился
задолго до падения сайта. За 90 дней страница не получила ни одного показа. То есть
SEO-страница под русский поиск не работает не из-за 404, а сама по себе — этим
придётся заниматься отдельно, после восстановления.

Sitemap Google последний раз читал 21.08.2026: заявлено 4 URL, **1 ошибка,
1 предупреждение**. Что именно — API не отдаёт, смотреть в веб-интерфейсе GSC
(«Файлы Sitemap» → строка sitemap.xml). Скорее всего это те же 404.

## Ahrefs: 5 групп проблем, одна причина

Все выгрузки Ahrefs (10.09.2026) описывают одно и то же падение с разных сторон.

| Отчёт Ahrefs | Строк | Что на самом деле |
|---|---|---|
| **Broken redirect** | 3 | Три канонических редиректа ведут на `https://odin-dva.ru/`, а он 404. Сломан не редирект, а его цель |
| **404 page** | 1 | Та же главная. `Depth 0`, `3 inlinks` — это корень сайта, на него ссылаются изнутри |
| **4XX page** | 1 | Дубль предыдущего, другой срез того же URL |
| **3XX redirect** | 3 | Те же три редиректа. `Is redirect loop: No` — цепочек и петель нет |
| **HTTP to HTTPS redirect** | 2 | `http://odin-dva.ru/` и `http://www.` → https. Это **норма**, отчёт информационный |

Важное, что видно из этих цифр: **сами редиректы настроены правильно.** Канонизация
идёт куда надо — с http на https и с www на голый домен, одним шагом 301, без цепочек
и петель. `Organic traffic 0` по всем строкам и `No. of redirect inlinks 0` — внешних
ссылок, которые бы теряли вес, нет.

Поэтому **чинить в Ahrefs нечего**. Главная отдаёт 200 с 10.09.2026, так что четыре
отчёта из пяти закроются сами при следующем обходе. Пятый (`HTTP to HTTPS redirect`)
останется — так и должно быть, это не ошибка.

Единственное, что стоит сделать, — перезапустить обход в Ahrefs вручную, не дожидаясь
планового: иначе отчёты неделю будут показывать старую картину.

## `.htaccess` на GitHub Pages не работает

В корне репозитория лежит [`.htaccess`](../../.htaccess) с MIME-типами для `.m4a`,
заголовками `Cache-Control` для `sw.js` и закомментированным принудительным HTTPS.
**GitHub Pages его не читает** — это конфиг Apache, а Pages работает на своей связке.

Практических последствий сейчас два:

- Заголовки `no-cache` для `sw.js` не применяются. Pages отдаёт свои, поэтому
  обновление Service Worker расходится не мгновенно. Обходится штатно — версией
  в `CACHE_NAME` внутри `sw.js`, она и так поднимается при каждом изменении.
- Принудительный HTTPS в `.htaccess` закомментирован и не нужен: его делает сам
  Pages настройкой `https_enforced`, она включена.

Файл не мешает и не отдаётся наружу (Pages скрывает точечные файлы), но держать
его в корне стоит только на случай переезда на обычный хостинг. Если переезда не
планируется — его можно удалить, чтобы не путал.
