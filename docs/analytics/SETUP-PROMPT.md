# Промт: подключить аналитику к новому проекту

Открыть Claude Code в папке нового проекта и вставить текст ниже целиком.
Эталон, на который он ссылается, — этот репозиторий (`~/Documents/webApp/1-2`).

Промт написан так, чтобы агент сам сходил в API и выяснил идентификаторы, а у тебя
спросил только то, чего в API нет. Ключи в текст не зашиты намеренно: они аккаунтные
и открывают доступ ко всем проектам сразу, а промт будет кочевать между папками.

Подходит и для статики на GitHub Pages, и для проектов на своём сервере: шаги 1-9
общие, а всё, что зависит от хостинга, вынесено в отдельные разделы — агент выбирает
нужный на первом шаге.

---

Подключи к этому проекту аналитику: Google Search Console, GA4, Яндекс.Метрику,
Bing Webmaster Tools и IndexNow. Эталонная реализация со всеми скриптами и
документацией — в `~/Documents/webApp/1-2`, бери её за основу и адаптируй.

## Что должно получиться

1. `scripts/seo/` — `fetch_gsc.py`, `fetch_ga4.py`, `fetch_metrika.py`, `fetch_bing.py`,
   `analyze.py`, `config.py`, `weekly.sh`. Скопировать из эталона и заменить константы
   под этот проект.
2. `secrets/` с `README.md`, вся папка в `.gitignore` кроме README.
3. `requirements-seo.txt`.
4. `docs/analytics/README.md` — доступы, ключи, идентификаторы, состояние подключений,
   первый замер с выводами.
5. Счётчики Метрики и GA4 в разметке сайта, если их там ещё нет.
6. События в коде приложения + гайд по заведению целей в Метрике.
7. Первая выгрузка данных и разбор.

## Порядок

### 1. Разведка — сначала выясни, что уже есть

Не спрашивай меня о том, что можно узнать из API или из кода. Проверь сам:

```bash
# какой домен у проекта
cat CNAME 2>/dev/null; grep -rn 'ALLOWED_HOSTS\|SITE_URL\|canonical' --include='*.py' --include='*.html' . | head

# какие счётчики уже стоят в разметке
grep -rn 'gtag\|googletagmanager\|mc\.yandex\|ym(\|msvalidate\|google-site-verification\|yandex-verification' --include='*.html' .

# что доступно ключам (пути — ниже, в разделе «Ключи»)
python3 scripts/seo/fetch_ga4.py --list
python3 scripts/seo/fetch_metrika.py --list
python3 scripts/seo/fetch_gsc.py --list
python3 scripts/seo/fetch_bing.py --sites
```

`--list` у GA4 покажет все ресурсы аккаунта, у Метрики — все счётчики, у Bing — все
подтверждённые сайты. Найди среди них наш по домену. Если ресурс GA4 неоднозначен,
сверь поток измерения с тем, что стоит в разметке:

```python
from google.oauth2 import service_account
from googleapiclient.discovery import build
creds = service_account.Credentials.from_service_account_file(
    "secrets/google-service-account.json",
    scopes=["https://www.googleapis.com/auth/analytics.readonly"])
a = build("analyticsadmin", "v1beta", credentials=creds, cache_discovery=False)
for s in a.properties().dataStreams().list(parent="properties/<ID>").execute().get("dataStreams", []):
    w = s.get("webStreamData", {})
    print(s.get("displayName"), w.get("measurementId"), w.get("defaultUri"))
```

Отдельно выясни, **как проект хостится и деплоится** — от этого зависит, куда класть
ключ IndexNow и как диагностировать недоступность сайта:

```bash
git remote -v                      # GitHub, свой Gitea, что-то ещё
ls .github/workflows/ deploy/ 2>/dev/null
cat CNAME 2>/dev/null              # есть — почти наверняка GitHub Pages
ls Containerfile Dockerfile docker-compose.yml manage.py 2>/dev/null
curl -sI https://<домен>/ | grep -i '^server'
```

`server: GitHub.com` — это Pages, дальше читай раздел «Если проект на GitHub Pages».
`Caddy`, `nginx`, отсутствие заголовка — свой сервер, читай «Если проект на своём
сервере». Разделы в конце файла.

Спрашивай меня только о том, чего в API нет: какой трафик считать своим (см. п. 5)
и какие действия в приложении измерять целями (см. п. 6).

### 4. Счётчики на сайте

Если Метрики или GA4 в разметке нет — добавь в `<head>` (в Django-проекте это
`templates/base.html`, в статике — каждая страница или общий шаблон). Туда же

### 5. Свои заходы не считать

На маленьком трафике пара своих открытий переписывает всю картину. Спроси меня,
из какой страны я захожу, и вырежи её **на уровне API**, а не при чтении отчёта, —
чтобы в CSV и в `TREND.md` попадали уже чистые цифры. Механика в `config.py`
эталона: у каждого сервиса свой формат названий стран (GSC — ISO alpha-3 строчными,
GA4 — английские названия, Метрика — на языке аккаунта, держи оба варианта).
Флаг `--include-self` должен отключать фильтр.

Покажи мне в документации таблицу «со своими заходами / без них» — разница обычно
неприятно большая, и это стоит видеть.

### 6. События и цели

Спроси меня, какие действия в приложении имеет смысл измерять. Обычно это 3-5 штук:
главное целевое действие, его завершение, создание чего-то своего, установка PWA.

Добавь в код одну обёртку на оба счётчика, по образцу `static/app.js` эталона:

```js
const YM_COUNTER_ID = <ID>;
function track(goal, params) {
  try { if (typeof ym === 'function') ym(YM_COUNTER_ID, 'reachGoal', goal, params); } catch {}
  try { if (typeof gtag === 'function') gtag('event', goal, params); } catch {}
}
```

Вызовы оборачивай в try/catch и проверяй `typeof` — счётчик может не загрузиться
(блокировщик, офлайн), и аналитика не имеет права ронять приложение.

Следи за двойным счётом. Классический пример: установка PWA, где срабатывают и
`userChoice`, и `appinstalled`. Считать надо один раз, в `appinstalled`, а источник
запоминать переменной.

Цели в Метрике я завожу руками — API создания целей требует `metrika:write`, а токен
у нас только на чтение. Напиши мне гайд с точными идентификаторами (см. грабли ниже,
там про интерфейс) и после сверь через API:

```bash
curl -sS -H "Authorization: OAuth $(cat secrets/yandex-metrika-token.txt)" \
  https://api-metrika.yandex.net/management/v1/counter/<ID>/goals
```

Проверь посимвольно, что идентификаторы совпадают с вызовами в коде, условие `exact`,
пробелов по краям нет, и что нет ни события без цели, ни цели без события.

### 7. Bing и IndexNow

Bing: подтвердить сайт (проще всего импортом из GSC, тогда мета-тег не нужен),
положить ключ в `secrets/bing-api-key.txt`. Первые 2-3 дня выгрузка пустая — это
норма, а не поломка.

IndexNow состоит из двух частей: ключ-файл, по которому поисковик убеждается, что
заявку шлёт владелец, и собственно отправка списка URL. Ключ генерируется
`secrets.token_hex(16)` и **не является секретом** — он публичен по построению.

Успешный ответ `api.indexnow.org` — **`HTTP 202`**, кода 200 протокол не возвращает.
Отправку всегда делай «мягкой»: сбой уведомления не должен ронять деплой.

Как отдавать ключ-файл — зависит от хостинга:

- **Статика:** положить `<ключ>.txt` в корень сайта, он поедет вместе с остальными
  файлами. Отправку добавить шагом после деплоя, с `continue-on-error`. Пример —
  `.github/workflows/pages.yml` эталона.
- **Django на сервере:** файлом на диске это обычно не сделать, у контейнера
  read-only ФС. Отдавать вью, как `robots.txt`. Готовая реализация —
  `~/Documents/webApp/clikme/apps/pages/indexnow.py`: ключ в `.env`, маршрут
  регулярный (`[0-9a-fA-F]{8,128}\.txt`), поэтому ключ меняется рестартом, а не
  передеплоем. **Маршрут ставить ПОСЛЕ `robots.txt` и `ads.txt`** — иначе он их
  перехватит. Отправку вешать на деплой-скрипт или на действие в админке.

## Грабли, общие для любого хостинга

Проверь их до того, как начнёшь чинить симптомы.

### GSC отдаёт итог, но постранично ноль строк

Порог приватности Google: пока данных мало, разбивку он скрывает. Не пиши в отчёте
«0 кликов» — это читается как «трафика нет вообще». Сверяй с итогом за период и
говори об этом прямо.

### Интерфейс Метрики переименован

«JavaScript-событие» теперь называется **«Целевое событие · ex JS-событие»**, плитка
первая в разделе «Пользовательские события». В поле идентификатора по умолчанию стоит
условие **«Содержит»** — переключить на **«Совпадает»**, иначе цель будет ловить любое
событие, в имени которого встречается строка.

**Цели считаются только с момента создания**, задним числом достижения не появляются.
Поэтому заводить их надо сразу, а не когда появится трафик.

### Структурированные данные и рейтинги

Google требует у `SoftwareApplication` поле `aggregateRating` или `review`, иначе
ругается на rich results. **Не рисуй рейтинг.** Разметка несуществующих отзывов —
нарушение правил, наказание за него не «сниппет не покажется», а ручные санкции на
весь сайт. Скажи мне об этом прямо и предложи честные варианты.

### Отчёты Ahrefs

Половина «проблем» — не проблемы. `3XX redirect` и `HTTP to HTTPS redirect` при
работающей канонизации домена информационные, «чинить» их значит ломать канонизацию.
`Title tag changed`, `H1 tag changed`, `Pages added to sitemaps` — фиксация наших же
правок между обходами. Когда сайт лежит, все отчёты Ahrefs описывают один и тот же
404 с разных сторон — не чини их по отдельности, найди общую причину.

### Правка markdown по якорям

Если правишь документацию скриптом с `t.index(...)` — проверяй, что якорь встречается
ровно один раз. Заголовок `# Bing Webmaster Tools` совпал с комментарием внутри примера
команды, и файл задвоился.

## Если проект на GitHub Pages

Признак: в корне лежит `CNAME`, `curl -I` отвечает `server: GitHub.com`.

### Сайт отдаёт 404 при зелёной сборке

**GitHub Pages не обслуживает приватные репозитории на бесплатном плане.** Сборка при
этом числится успешной, никаких предупреждений нет. Проверка — сравнить с публичным
репозиторием того же аккаунта.

```bash
gh api repos/<owner>/<repo> --jq '.private'
gh api repos/<owner>/<repo>/pages --jq '"cname=\(.cname) status=\(.status)"'
gh api repos/<owner>/<repo>/actions/permissions   # enabled должно быть true
```

### Ничего не деплоится, а сборка «queued»

**Выключенные GitHub Actions.** Встроенный конвейер Pages — тоже workflow, поэтому с
`enabled: false` он молчит, а `POST /pages/builds` отвечает `queued` и не делает ничего.
Лечится `PUT /actions/permissions -F enabled=true`. Отключается заодно с Pages, когда
репозиторий переводят в приватный на бесплатном плане.

### `The custom domain is already taken`

Осиротевшая запись от прежней привязки. Ни за каким другим репозиторием домен при этом
не числится. Снимается только подтверждением владения через TXT-запись, API для этого
нет — github.com/settings/pages → Add a domain. У reg.ru `ns1` и `ns2` расходятся на
несколько минут, жать Verify стоит когда оба отвечают одинаково:

```bash
dig +short TXT _github-pages-challenge-<user>.<domain> @ns1.reg.ru
dig +short TXT _github-pages-challenge-<user>.<domain> @ns2.reg.ru
```

### `The certificate does not exist yet`

Домен и HTTPS ставятся раздельно: сертификат выпускается только после привязки домена.
Сначала `-f cname=...`, потом `-F https_enforced=true`.

### Что публикуется наружу

Легаси-конвейер Pages выкладывает **корень репозитория целиком** — то есть `docs/`,
`scripts/` и всё остальное, что ты добавишь, окажется в вебе. Собирай содержимое сайта
явно, по списку исключений (не включений — тогда новая страница поедет сама), и проверь
после деплоя:

```bash
curl -o /dev/null -w '%{http_code}\n' https://<домен>/docs/analytics/README.md   # ждём 404
```

## Если проект на своём сервере

Признак: `Caddy`/`nginx` в заголовке `server`, есть `Containerfile`, `manage.py`,
`deploy/`. Эталон такого проекта — `~/Documents/webApp/clikme`.

### Куда класть счётчики и мета-теги

В общий шаблон, обычно `templates/base.html`, а не в каждую страницу. Туда же
`google-site-verification`, `yandex-verification`, `msvalidate.01`.

### robots.txt и sitemap.xml генерируются приложением

В статике это файлы в репозитории, здесь — маршруты. Значит:

- запасной вариант «взять sitemap из репозитория, если живой недоступен» (он есть в
  `fetch_gsc.py` эталона) тут бесполезен — лежащий сайт не отдаст ни живой, ни локальный;
- проверять надо не наличие файла, а ответ маршрута: `curl -sI https://<домен>/robots.txt`;
- если карта постраничная (`sitemap_index`), `--inspect` берёт вложенные карты сам,
  но упрётся в квоту 2000 URL в сутки — ограничивай выборку.

### Read-only файловая система контейнера

Ничего, что нужно отдать по конкретному URL, нельзя просто положить файлом. Ключ
IndexNow, `ads.txt`, подтверждения — всё отдаётся вью. Порядок маршрутов имеет
значение: регулярный маршрут ключа IndexNow перехватит `robots.txt`, если поставить
его выше.

### Сайт недоступен — что проверять

Здесь нет «зелёной сборки», которая врёт, зато больше слоёв. По порядку:

```bash
curl -sI https://<домен>/ | head -3          # что за сервер отвечает и отвечает ли
curl -sI http://<домен>/ | head -3           # редирект на https настроен?
echo | openssl s_client -servername <домен> -connect <домен>:443 2>/dev/null \
  | openssl x509 -noout -dates                # сертификат не протух?
dig +short A <домен>                          # DNS ведёт куда надо?
```

Дальше — на сервере: жив ли контейнер, что в логах прокси, не кончилось ли место.
Не гадай по симптомам: 502 от прокси, 404 от приложения и 404 от прокси — три разные
поломки, и различаются они заголовком `server` и телом ответа.
